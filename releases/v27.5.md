# Release Notes — Workflow v27.5

**Type:** Bug fix (release candidate) · **Status:** NOT DEPLOYED (production of record remains v26.9)
**Date:** 2026-07-31 · **Supersedes:** v27.4 · **Fixes:** [BUG-009](../bugs/BUG-009.md)
**Investigation:** [INV-009](../investigations/INV-009.md) · **Plan:** [INV-009-PLAN.md](../investigations/INV-009-PLAN.md) (Option A — minimal fix)

---

## Summary

Returning customers could not be identified because `Return Customer Lookup` fell
back to the parent workflow's phone (a placeholder/test number in the reported
call) instead of the valid active-session phone. This release fixes the timezone
handling that caused a fresh session to be wrongly judged stale.

## Root cause (confirmed — INV-009)

`Return Customer Lookup` parsed the Sessions-sheet `stored_at` with timezone-naive
`new Date()` for its 2-hour freshness gate. `stored_at` is written as a Toronto
wall-clock string with no offset (`Store Phone in Static Data`), and the workflow
sets no timezone, so `new Date()` used the n8n process timezone (default UTC). The
~4-hour Toronto offset inflated the computed age past the 2-hour window, so a fresh
session phone was discarded and the code fell back to `trigger.caller_phone`
(`+16135551212` → `searchedPhone = 6135551212`).

## Change

Reused the **existing** timezone-aware parsing from the `Filter Old Sessions` node
(no new parsing implementation): a small helper

```
parseStoredAtMs(v): DateTime.fromISO(v)  ||  DateTime.fromFormat(v, 'ccc, LLL d, yyyy h:mm a', { zone: 'America/Toronto' })  → epoch ms | null
```

applied to **both** the newest-session sort and the 2-hour freshness gate in
`Return Customer Lookup`.

## Workflow nodes modified

| Node | Type | Change |
|---|---|---|
| `Return Customer Lookup` | code | Added `parseStoredAtMs()` (reusing the Filter Old Sessions approach); replaced the two `new Date(stored_at)` parses (sort + freshness gate) with it. No other logic changed. |

**Exactly one node changed.** No sibling node modified; no rewiring; connections
and workflow `settings` byte-identical to v27.4; no Google Sheets schema change; no
prompt/integration change. Verified: the only node differing between v27.4 and
v27.5 is `Return Customer Lookup`.

## Behavior change (scope)

Only the session-phone freshness decision changes: a valid current session phone is
now correctly preferred regardless of the n8n process timezone. All other
behavior — fallback to parent when no valid session exists, the "ask for the
number" prompts, customer matching, and the output contract to the
`lookup_customer` tool — is unchanged.

## Regression results

Documented BUG-009 scenarios were executed as logic simulations under **both**
`TZ=UTC` (n8n default) and `TZ=America/Toronto`. All pass:

| Scenario | Expected | Result |
|---|---|---|
| S1 valid current session (BUG-009 evidence values) | session phone `4372415892`; customer found | PASS |
| S2 expired session (>2h) | fallback to parent | PASS |
| S3 missing session | fallback to parent | PASS |
| S4 valid session + parent placeholder present | session phone wins | PASS |
| S5 new customer (session ok, no match) | ask if different number | PASS |
| S6 empty everywhere | ask for the number | PASS |
| Timezone independence | identical correct results under UTC and Toronto | PASS |

Old-vs-new contrast on S1: OLD used `6135551212` (customer **not** found); NEW uses
`4372415892` (customer found). Note: these are logic simulations in this
environment; formal verification against live n8n + Google Sheets remains part of
the QA gate before deployment.

## Deployment status

Release candidate, **NOT DEPLOYED**. Production of record remains `workflow-v26.9.json`.
Promotion to production requires a QA-gate PASS and deployment per `OPERATIONS.md`.

## Rollback

The change is confined to one node's code. Rollback = redeploy the previous
candidate `workflow-v27.4.json` (retained at top level) or the production of record
`workflow-v26.9.json`. No data migration or schema change is involved, so rollback
is immediate and safe.

## Follow-up (not in this release)

INV-009 notes a secondary weakness (session selection is unscoped to the current
`call_sid`) and a latent consistency gap (sibling nodes use naive `new Date()` only
for sorting). Per the approved plan these are deliberately **out of scope** for
this minimal fix and should be handled as a separate hardening ticket (Option B).
