# BUG-006

**Bug ID:** BUG-006
**Title:** Appointment lookup and reschedule flow fails to reliably identify existing appointments
**Severity:** High (provisional — confirm during investigation)
**Status:** Open
**Date:** 2026-07-28 (added to tracker). Original report date: Unknown — not recorded in repository.

---

## Description

The appointment lookup and reschedule path does not reliably match an existing
appointment for a known caller.

## Business Impact

A caller with a real appointment can be told none is found or be unable to
reschedule — a customer-facing failure that can cause missed appointments,
unnecessary human transfers, and lost trust.

## Expected Behaviour

- [`DECISIONS.md`](../DECISIONS.md) — "Appointments record as identifier source of
  truth": cancellation and rescheduling resolve the calendar event ID from the
  Appointments record by caller phone (status `Booked`/`Rescheduled` only);
  AI-spoken identifiers are fallback only.
- [`docs/tools/reschedule_appointment.md`](../docs/tools/reschedule_appointment.md):
  `lookup_customer` runs first to identify the caller and their appointment.
- [`docs/workflows/customer-lookup.md`](../docs/workflows/customer-lookup.md)
  defines lookup and its failure handling.

## Actual Behaviour

Reported: the lookup/reschedule flow fails to reliably identify an existing
appointment for a known caller. Not independently reproduced in this documentation
pass — reproduction and confirmation are pending investigation.

## Steps to Reproduce

Unknown — requires investigation. Proposed starting point (not yet executed): for
a caller with a known active appointment, exercise `lookup_customer` /
`lookup_appointment` and the reschedule path and observe whether the appointment
is matched, paying attention to the phone value used for matching and the status
filter applied.

## Investigation Status

Not started. Open — investigation required.

## Root Cause

Unknown — requires investigation.

Candidate areas to examine (unconfirmed — starting points only):
- Phone-number matching. BUG-001 established that a bare-10-digit vs E.164 (`+1…`)
  divergence broke a phone-based row match elsewhere (`DECISIONS.md`, "Canonical
  phone format is E.164"). Whether a similar mismatch affects lookup is the
  specific question.
- The status filter (`Booked`/`Rescheduled` only) and non-empty-identifier
  condition used when locating the active appointment
  (`docs/tools/cancel_appointment.md`, `docs/tools/reschedule_appointment.md`).
- Lookup-failure handling paths (`docs/workflows/customer-lookup.md`,
  `docs/tools/lookup_appointment.md`, `docs/tools/lookup_customer.md`).

## Acceptance Criteria

- A caller with an active appointment (`Booked`/`Rescheduled`) is reliably matched
  by the lookup and reschedule paths.
- Matching is robust to the phone formats that occur in production.
- No fallback to another customer's appointment (privacy rule preserved,
  `CHANGELOG.md` V26.0).

## Engineering Notes

Confirm behavior against the deployed artifact (`production/workflow-v26.9.json`)
with real caller-phone values before assigning a cause. The phone-format class of
defect has bitten this project before (BUG-001), making it a priority hypothesis
to rule in or out — but it must be confirmed by evidence, not assumed.

## Regression Requirements

To be defined once the root cause is confirmed. Guards would live in
`tests/reschedule.md` and the lookup-related scenarios, asserting reliable
identification across phone-format and status variations.
