# BUG-009

**Bug ID:** BUG-009
**Title:** Return Customer Lookup ignores the active session phone and falls back to the parent workflow placeholder phone
**Severity:** High
**Priority:** High
**Status:** Implemented
**Deployment Status:** Not Yet Deployed
**Date Created:** 2026-07-29 (specification supplied and documented).
**Date Updated:** 2026-07-31 (Option A fix implemented in Workflow v27.5; regression passed — see releases/v27.5.md).

---

## Description

During Return Customer Lookup, the workflow sometimes ignores the valid phone
number stored in the active session and instead performs the customer lookup using
the placeholder phone number received from the parent workflow.

This causes customer lookup to fail even though the correct phone number is
available.

## Business Impact

- Existing customers cannot be identified.
- Customer lookup fails.
- Rescheduling may fail.
- Cancellation may fail.
- Existing customers may be treated as new customers.
- The AI unnecessarily asks whether the customer booked under another phone number.

## Evidence

| Source | Value |
|---|---|
| Active Session Phone | `caller_phone = 14372415892` |
| Parent Workflow | `caller_phone = +16135551212` |
| Lookup Result | `searchedPhone = 6135551212` |

The lookup searched using the parent-workflow (placeholder) phone rather than the
valid active-session phone.

**Confirmed during investigation (INV-009, against dev workflow v27.4).** The same
`stored_at` field is parsed two ways in the workflow: `Return Customer Lookup` uses
timezone-naive `new Date()`, while `Filter Old Sessions` uses zone-aware luxon
(`fromFormat(..., { zone: 'America/Toronto' })`). Node-accurate reproduction under
the n8n-default UTC timezone on a session stored seconds earlier:
`Return Customer Lookup` computes age **4.01 h → fails the 2-hour gate**, whereas
`Filter Old Sessions` computes **0.01 h → passes**. `normPhone('+16135551212')` →
`6135551212` = the reported `searchedPhone`, proving the fallback branch executed
while a valid session phone (`14372415892` → `4372415892`) existed.

## Expected Behaviour

Lookup priority must always be:

1. Active Session Phone.
2. Parent Workflow Phone (only if no valid session phone exists).
3. Ask the customer for the booking phone number.

The workflow must never use placeholder or test phone numbers when a valid session
phone exists.

## Actual Behaviour

The workflow ignored the active session phone and instead searched using the
placeholder phone (`searchedPhone = 6135551212`, derived from the parent-workflow
value rather than the session value).

## Steps to Reproduce

Reported with the evidence above (active session `14372415892`, parent
`+16135551212`, resulting `searchedPhone = 6135551212`). A precise reproduction
sequence against the deployed artifact is to be confirmed during investigation.

## Root Cause

**Confirmed — workflow logic** (full evidence in
[`investigations/INV-009.md`](../investigations/INV-009.md)). In the current
development workflow (`production/workflow-v27.4.json`), the `Return Customer
Lookup` code node parses the session `stored_at` with timezone-naive `new Date()`
for both its newest-session sort and its 2-hour freshness gate. `Store Phone in
Static Data` writes `stored_at` as a Toronto wall-clock string with no offset, and
the workflow sets no `settings.timezone`, so `new Date()` uses the n8n process
timezone (default UTC). The mismatch inflates the computed age by the Toronto UTC
offset (~4 h), exceeding the 2-hour window, so a valid current session phone is
judged stale and discarded; the code falls back to the parent trigger phone
(`trigger.caller_phone` = `+16135551212` → `searchedPhone = 6135551212`).

This is proven to be a code defect (not an environmental accident) because the same
repository parses the identical `stored_at` field **correctly** — zone-aware luxon
— in the `Filter Old Sessions` node. Reproduced deterministically (Evidence above).

Secondary weakness: `Read Session Phone` is unfiltered and selection is
"most-recent across all sessions," not scoped to the current call's `call_sid` —
a concurrency risk independent of the timezone defect.

Affected nodes: `Return Customer Lookup` (proximate); `Store Phone in Static Data`
and `Read Session Phone` (secondary). The same naive `new Date(stored_at)` pattern
also appears in `Code2`, `Set Data1`, `Code4`, `Set Data2`, `Cancel Appointment
Context`, `End Call Context`, and `Return Appointment Lookup` — see INV-009 Risks.

Fix implemented (Option A) in Workflow **v27.5** — see Implementation Notes below.

## Implementation Notes

Fixed per the approved **Option A** plan ([INV-009-PLAN.md](../investigations/INV-009-PLAN.md)),
in the current development head, producing release candidate
**`production/workflow-v27.5.json`** (supersedes v27.4; NOT deployed).

- **Node modified (exactly one):** `Return Customer Lookup` (code). No sibling node
  touched, no rewiring, no connection/settings change, no sheet-schema change.
- **Change:** reused the **existing** timezone-aware parsing from the `Filter Old
  Sessions` node (per the implementation requirement — no new parser). Added a
  `parseStoredAtMs()` helper (luxon `DateTime.fromISO` → `fromFormat(..., { zone:
  'America/Toronto' })` → epoch ms) and applied it to both the newest-session sort
  and the 2-hour freshness gate, replacing the timezone-naive `new Date(stored_at)`.
- **Behavior scope:** only the session-phone freshness decision changes — a valid
  current session phone is now correctly preferred regardless of the process
  timezone. Fallback, prompts, matching, and the tool output contract are unchanged.
- **Regression:** all documented BUG-009 scenarios pass under both UTC and
  America/Toronto (details in [releases/v27.5.md](../releases/v27.5.md)). These are
  logic simulations in this environment; live-n8n QA-gate verification is
  outstanding, hence Status **Implemented** (not Verified) and Deployment Status
  **Not Yet Deployed**.

## Engineering Notes

Investigated per the documented process against the current development workflow
`production/workflow-v27.4.json` (INV-009, 2026-07-31); the relevant nodes are
byte-identical in the production of record `workflow-v26.9.json`. The bug was
**reproduced** deterministically, and the root cause is a confirmed **workflow-logic**
defect (timezone-naive `new Date()` parse of `stored_at`), decisively evidenced by
the correct zone-aware parse of the same field in the `Filter Old Sessions` node.
The naive pattern recurs across sibling session nodes (booking/reschedule/cancel/
end-call/appointment-lookup), which matches this bug's impact on rescheduling and
cancellation and widens the regression scope (see INV-009 Risks).

Related in theme to [BUG-006](BUG-006.md) (lookup/reschedule reliably identifying
appointments) and to the phone-format lessons of [BUG-001](BUG-001.md) — these are
cross-references for the investigator, not a claim of shared root cause. Per
process (`AI_ENGINEERING_RULES.md` Rules 9–10), the confirmed root cause does not
authorize a fix; findings are presented and must be explicitly approved before any
implementation. Status intentionally left at **Confirmed**; not marked fixed.

## Regression Requirements

Regression must cover, at minimum: valid session (session phone used), expired
session, missing session, fallback-to-parent behaviour only when no valid session
phone exists, and placeholder/test-number rejection. Scenarios to live in
`tests/reschedule.md` / the lookup scenarios once the fix is defined.
