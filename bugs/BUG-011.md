# BUG-011

**Bug ID:** BUG-011
**Title:** Call does not hang up after the goodbye (caller-silent path) — assistant says farewell but the call stays connected
**Severity:** High (customer-facing; leaves the caller on a dead line and consumes telephony minutes)
**Priority:** High
**Status:** Confirmed
**Deployment Status:** N/A (no fix implemented)
**Date Created:** 2026-08-07.
**Date Updated:** 2026-08-07 (investigation complete — see INV-011).

---

## Description

When the caller becomes silent, the assistant delivers the two-step silence script and
the farewell ("…Feel free to call us back whenever you're ready. Have a great day!"),
then is instructed to call `end_call`. The phone call, however, does not end — the
assistant says goodbye but the line remains connected.

## Business Impact

Callers are left on a dead line after the goodbye; the call continues to consume
telephony minutes (Twilio billing) and ties up the line/agent capacity. Poor customer
experience and avoidable cost. Not data-corrupting.

## Expected Behaviour

After the silence farewell, `end_call` runs and the Twilio call is **actually
disconnected** (media stream closes, conversation ends), promptly and reliably —
per `docs/tools/end_call.md` ("Terminates the phone call through the telephony
provider after the AI has said its farewell").

## Actual Behaviour

The assistant says the farewell and (per the prompt) calls `end_call`, which returns
`success=true, end_call=true`, so the AI stops talking — but the Twilio call is **not
disconnected** and the line stays open.

## Investigation Status

Complete — see [`investigations/INV-011.md`](../investigations/INV-011.md) (2026-08-07,
revised). The **architectural risk is confirmed** from repository evidence; the
**production failure mechanism is not yet confirmed** — it depends on runtime behavior
and requires execution artifacts (n8n execution, ElevenLabs tool invocation, Twilio API
response, resolved `callSid`, `end_call` input payload — see INV-011 "Required
evidence").

## Evidence

- The prompt instructs the farewell + `end_call` after two silent prompts
  (prompt-v28/29 L303–309, L316–322: "IMMEDIATELY call end_call with reason
  'caller_silent'", "Never skip end_call"). The reported phrase matches Step 2.
- The prompt calls `end_call` with `reason` only and **never passes `system__call_sid`**,
  although `docs/tools/end_call.md` and `tests/tool-behavior.md` L93 require it.
- The workflow hangup is SID-gated: `End Call Context → Valid Call SID? →` TRUE:
  `Wait Before Hangup → Twilio - End Call (POST .../Calls/{sid}.json Status=completed)
  → Twilio - Redirect to Hangup TwiML → Return End Call Success`; FALSE:
  `Return No SID Error` (no hangup; note "Twilio will time out the call").
- Both terminal nodes return `success=true, end_call=true` — success is reported even
  when no hangup occurs.
- The "no SID → provider times the call out" behavior is the documented design
  (`tests/edge-cases.md` L111; `tests/tool-behavior.md` L95).
- Present identically in production (v26.9 / prompt-v28) and dev head (v27.5 /
  prompt-v29). Full confirmed/inferred/unknown breakdown in INV-011.

## Root Cause

**Confirmed — architectural (repository evidence):** (a) the prompt omits the
`system__call_sid` input that the `end_call` contract requires, removing the most direct
call-SID source; (b) when no call SID is resolved, the workflow performs **no hangup**
and returns `end_call=true` with a "provider timeout" note; and (c) **both** terminal
responses report `success=true` regardless of the telephony outcome. Together these are a
confirmed **architectural risk**: a termination path that can report success while
performing no disconnect.

**Inferred (runtime-dependent, NOT confirmed from the repository):** that the "provider
timeout" does not actually disconnect a live, silent Twilio call, and therefore that the
no-SID path (or a failed Twilio hangup) is what produced the reported symptom.

**Production failure mechanism: Unknown — requires additional evidence** (see INV-011
"Required evidence": n8n execution, ElevenLabs tool invocation, Twilio API response,
resolved `callSid`, `end_call` input payload). The repository confirms the architectural
risk but cannot yet confirm which mechanism fired in the reported call.

## Acceptance Criteria

- After the silence farewell, the live Twilio call is actually disconnected promptly
  and reliably (verified on a live call), not merely reported as `success=true`.
- Termination does not depend on an unreliable "provider timeout"; the no-SID case
  either resolves a SID or fails safe (surfaces a real failure) rather than silently
  leaving the call open.
- `end_call` receives the inputs its contract requires (`reason`, and
  `system__call_sid` when applicable).
- `human_handoff` call transfer remains unaffected.

## Regression Requirements

Silence two-step → actual disconnect; natural-conclusion / abusive-after-warning /
robocall → disconnect; no-stored-SID scenario → the call actually ends (not just
`success=true`); `human_handoff` transfer unaffected; live Twilio verification that the
call truly hangs up. Include both production (v26.9/prompt-v28) and dev-head
(v27.5/prompt-v29) contexts.

## Engineering Notes

Distinct from BUG-009 (session-phone timezone parse) and BUG-010 (booking confirmation
UX), though it shares the family trait that a terminal node reports `success=true`
regardless of the real telephony outcome, and a dependency on `call_sid` captured at
call start by `/setVar`. The smallest candidate change (prompt: pass `system__call_sid`)
only helps if ElevenLabs supplies that variable; the "call never ends" symptom on the
no-SID path likely needs a workflow/architecture change plus live verification. Per
process (`AI_ENGINEERING_RULES.md` Rules 9–10), a confirmed root cause does not
authorize a fix; options are recorded in INV-011 and require explicit approval.

## Risk Assessment

`end_call` runs at the end of every call, so changes risk ending calls prematurely or
failing to end them; it shares Twilio call-control mechanisms with `human_handoff`. The
fix's effectiveness depends on ElevenLabs configuration and Twilio credentials/account
SID (partly outside the repository), so a **live call test is required**. Suggested
severity **High** (customer-facing + billing), not data-corrupting.
