# BUG-002

**Bug ID:** BUG-002
**Title:** Call_Records rows created but most fields read `unknown`/`not_configured`
**Severity:** High
**Status:** Implemented
**Deployment Status:** Not Yet Deployed
**Date:** Unknown — not recorded in repository. Fix implemented in Workflow V27.3. Documented in tracker 2026-07-28.

---

## Description

Once the post-call chain ran (after BUG-001), `Call_Records` rows were created but
most columns read `unknown` or `not_configured`.

## Business Impact

The per-call instrumentation carried no usable signal, so monitoring metrics
derived from Call Records (duration, tools fired, outcome) were unreliable.

## Expected Behaviour

Per [`docs/data-model/call-records.md`](../docs/data-model/call-records.md): the
payload-derived fields (Duration Secs, Tools Fired, Outcome, Call SID, etc.)
populate from the received ElevenLabs post-call webhook payload; every column is
always populated and sheet-safe.

## Actual Behaviour

`metadata`/`analysis`/`collected`/`dynvars` read empty and `transcript` was
absent, so payload-derived fields degraded to sentinels. The Payload Shape
diagnostic showed `data:[conversationId, callerPhone, notesText, timestamp]` —
`Build Call Record` was reading the output of `Parse Post Call Data`, not the raw
webhook.

## Steps to Reproduce

Recorded in `CHANGELOG.md` (Workflow V27.3); covered by probes I-18/I-19 in
`tests/instrumentation.md`. Signature: a real payload was received yet the Call
Record reports `metadata:[]` / `analysis:[]` / `transcript:absent`.

## Investigation Status

Complete. Root cause confirmed via the Payload Shape diagnostic column.

## Root Cause

Introduced by Workflow V27.2 Fix 3. Decoupling moved `Build Call Record` onto an
independent branch driven from `Parse Post Call Data`, so `$json` became the
parser's output rather than the raw webhook body. The branch architecture was
correct; the payload *source* was wrong.

## Files Involved

- `production/archive/workflow-v27.3.json` (fix). Node changed: `Build Call Record`
  (1 node). Connections identical to V27.2.
- `docs/data-model/call-records.md` records the absolute-reference requirement.

## Implemented Fix

- `Build Call Record` reads the payload via an **absolute** reference —
  `$('ElevenLabs Post Call Webhook').first().json` — with a graceful `$json`
  fallback. Restores metadata/analysis/transcript without re-coupling to the notes
  chain.
- Added a Call SID fallback to workflow static data
  (`$getWorkflowStaticData('global').call_sid`) for payloads that omit the SID.
- Scope: 1 node. No booking/scheduling/calendar/reminder-SMS/prompt/customer node
  touched. Monitoring schema unchanged (13 columns).

## Acceptance Criteria

- With the real payload reachable, Duration Secs, Tools Fired, Outcome populate.
- Call SID falls back to static data when omitted.
- The node degrades gracefully (13 columns, no throw) if the webhook reference
  returns nothing.
- The V27.2 notes-branch decoupling is preserved.

## Regression Requirements

`tests/instrumentation.md` I-18 (reads webhook payload, not parser output) and
I-19 (Call SID falls back to static data). Any future edit to `Build Call Record`
must preserve the absolute reference; reading `$json` as the payload reintroduces
this bug (`docs/data-model/call-records.md`).
