# BUG-003

**Bug ID:** BUG-003
**Title:** Placeholder appointment row created on every first-time booking
**Severity:** Low (data pollution — write-only, no reader)
**Status:** Implemented
**Deployment Status:** Not Yet Deployed
**Date:** Unknown — not recorded in repository. Fix implemented in Workflow V27.4. Documented in tracker 2026-07-28.

---

## Description

Every time a first-time customer booked, the booking flow appended a fake
appointment row with Appointment ID `___NO_OLD_APPOINTMENT___` and Status
`Rebooked`.

## Business Impact

Low. The placeholder was write-only: no node reads it and no node filters on
`Rebooked` status (the reminder engine uses positive inclusion of
`booked`/`rescheduled`), so it was data pollution rather than a functional or
customer-facing failure.

## Expected Behaviour

Per [`tests/booking.md`](../tests/booking.md): a first-time booking writes exactly
one real appointment row and no placeholder; a returning customer's previous row
is updated to `Rebooked` and its calendar event deleted — a single new row, no
duplicate.

## Actual Behaviour

For first-time customers (empty `oldAppointmentId`), a placeholder row was
appended with Appointment ID `___NO_OLD_APPOINTMENT___`, Status `Rebooked`.

## Steps to Reproduce

Book as a first-time customer (a phone with no existing appointment). Before the
fix, an extra `___NO_OLD_APPOINTMENT___`/`Rebooked` row appeared alongside the real
booking. Covered by the `tests/booking.md` BUG-003 scenario and its preservation
scenario.

## Investigation Status

Complete. Root cause confirmed and recorded in `CHANGELOG.md` (Workflow V27.4).

## Root Cause

The booking flow always runs a supersede sub-chain (`Extract Old Event ID` →
`Delete Old Calendar Event` → `Mark Old Appointment Rebooked`) to overwrite a
returning customer's previous appointment. For first-time customers
`oldAppointmentId` is empty. `Mark Old Appointment Rebooked` was
`operation=appendOrUpdate`, matching on Appointment ID with a fallback of
`___NO_OLD_APPOINTMENT___`; the sentinel matched no row, so `appendOrUpdate`
**appended** a fake row.

## Files Involved

- `production/workflow-v27.4.json` (fix). Node changed: `Mark Old Appointment
  Rebooked` (exactly 1 node). Status/Notes column mappings unchanged. Connections
  identical.

## Implemented Fix

- Changed `Mark Old Appointment Rebooked` to `operation=update` with
  `alwaysOutputData=true`, and removed the sentinel fallback. Returning customer:
  the real row is still matched and updated to `Rebooked` — identical behaviour.
  First-time customer: the empty ID matches nothing and updates nothing (no fake
  row); `alwaysOutputData` keeps the item flowing to `Restore Payload` so the real
  appointment write and the rest of the booking chain are unaffected.
- A Filter/IF was rejected: filtering first-time items out would remove them from
  the booking chain entirely (downstream `Restore Payload` and the real append),
  preventing the real appointment from being written.
- Scope: exactly 1 node. No booking, rescheduling, cancellation, lookup, SMS,
  calendar, or monitoring node touched.

## Acceptance Criteria

- A first-time booking writes one real row and no placeholder.
- A returning customer's previous row is still marked `Rebooked` with its calendar
  event deleted and exactly one new row written.
- The rest of the booking chain is unaffected.

## Regression Requirements

`tests/booking.md` — "First-time customer booking creates no placeholder row
(BUG-003)" and "Returning customer rebooking still marks the old appointment
(BUG-003 preservation)".
