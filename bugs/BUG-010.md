## Description

Two conversational/UX issues in the booking flow:

- **A — Over-confirmation.** During booking, the AI reads the appointment details
  back to the caller up to three times: once before checking availability, once as
  the pre-booking summary, and once in the success message. Only one full read-back
  (the pre-booking summary) is intended.
- **B — Spoken phone formatting.** When speaking the phone number, the assistant
  reads the stored E.164 value including the domestic country code — e.g.
  `+1 437 241 5892` → "one four three seven …" — rather than the 10-digit national
  number.

## Business Impact

Degraded conversational experience: the call feels repetitive and longer than
necessary (A), and the spoken phone number is awkward and harder for the caller to
verify (B). No effect on data integrity, calendar, booking correctness, or SMS
delivery (storage stays E.164).

## Expected Behaviour

- **A:** Per `docs/conversations/booking-conversation.md` and the intended UX: one
  full appointment summary before booking (read-back → confirm → book), then **one
  concise** success confirmation. The caller should not hear essentially the same
  details three times.
- **B:** Keep storing/passing phone numbers internally as full **E.164**
  (`+1XXXXXXXXXX`). When *speaking* to the customer, **omit the domestic country
  code `1`** and read the **complete 10-digit** number, grouped — e.g. "four three
  seven, two four one, five eight nine two" or "437-241-5892". Do **not** truncate
  or read only the last four digits; the entire 10-digit number must be spoken so
  the caller can catch an error anywhere in it.

## Actual Behaviour

- **A:** Three restatements: (1) "Just to confirm, you have a 2012 BMW 325…" before
  the availability check; (2) "Just to confirm — I have you down as Ivan…" before
  booking; (3) "You're all set… I have you down as Ivan… with the [vehicle] for
  [service]…" after booking.
- **B:** The `[phone]` read aloud in the summary (#2) and success (#3) is the E.164
  value with the country code, e.g. spoken as "one four three seven two four one
  five eight nine two".

## Steps to Reproduce

Complete a normal booking conversation (provide vehicle/service/time/name) and
observe: the assistant's turns before availability, before booking, and after
booking (A); and how the phone number is spoken in the summary and success message
(B). Full annotated timeline in [`investigations/INV-010.md`](../investigations/INV-010.md).

## Investigation Status

Complete — see [`investigations/INV-010.md`](../investigations/INV-010.md) (2026-08-04, revised).

## Root Cause

Two sub-issues; **not** workflow or tool-response duplication (both are concise).

- **#2 (pre-booking summary)** is the single intended read-back — `prompt-v28.txt`
  L192–200 and the `book_appointment` tool description. Correct.
- **#3 (success)** is **prompt-driven and verbose**: the success template
  (`prompt-v28.txt` L208–210) re-reads name/vehicle/service/date/phone, even though
  the workflow's tool `message` is concise (`"Booked for [date] at [time]."`,
  `Return Booking Success`).
- **#1 (pre-availability read-back) — origin unknown.** The repository evidence only
  establishes that it does **not** originate from the workflow, the tool responses,
  or the documented prompt. It is likely produced by behavior outside the repository
  (for example, emergent model behavior or ElevenLabs configuration such as
  agent-level instructions), but **this has not been confirmed** — no model trace or
  ElevenLabs console configuration was available to this investigation. Not
  classified as confirmed LLM behavior.
- **B (spoken phone formatting).** The phone value is E.164 (`Set Data1`
  `normalizePhone` → `+1XXXXXXXXXX`; prompt `PHONE NUMBER RULES` L102–115 format as
  `+1XXXXXXXXXX`); the summary/success templates read `[phone]` **verbatim**
  (`prompt-v28.txt` L195, L209); and the prompt contains **no rule for how to
  vocalize a phone number**, so the E.164 value (with the `1`) is read aloud.
  Storage is correct — the issue is only how the number is spoken.

## Files Involved

- `production/prompt-v28.txt` — success template (L208–210); mandatory summary
  (L192–200); `get_availability` section (no read-back instruction, re: #1);
  `PHONE NUMBER RULES` (L102–115) and the two spoken `[phone]` templates (L195,
  L209), re: B.
- (Reference, not a cause) `production/workflow-v27.5.json` — `Return Booking
  Success` / `Prepare Booking Payload` return a concise message; `Set Data1`
  `normalizePhone` produces E.164 (correct for storage).

## Implementation Notes

Fixed (prompt-only, smallest change) in **`production/prompt-v29.txt`** (supersedes
prompt-v28; NOT deployed). No workflow, tool, Google Sheets, Calendar, or storage
change — `workflow-v27.5.json` and `prompt-v28.txt` are byte-identical to before.
Three localized prompt edits:

1. **Concise success confirmation (A):** the post-booking message now confirms
   completion + date/time and keeps the pricing disclaimer + technician note, without
   re-reading name/vehicle/service/phone (L214).
2. **Read-once guard (A):** expanded the confirmation-step rule — the complete summary
   is read back exactly once, immediately before booking, and not before/just after
   the availability check (L206). The mandatory pre-booking summary is preserved.
3. **Spoken phone rule (B):** added a vocalization rule under PHONE NUMBER RULES —
   speak the full 10-digit national number without the leading "1", grouped
   (`+14372415892` → "437-241-5892"), never truncated; storage/tool inputs stay E.164
   (L112–117).

**Regression (all PASS):** exactly one mandatory pre-booking summary; read-once /
not-before-availability guard present; success message concise; spoken phone =
10-digit national (no `+1`, grouped, no truncation); E.164 storage/tool-input rules
preserved; Explicit-Confirmation contract preserved; "never say booked unless
success=true AND booked=true" preserved; pricing disclaimer preserved. Details in
[`releases/prompt-v29.md`](../releases/prompt-v29.md). These are prompt-content
checks; **live-call verification is part of the QA gate**, so Status is
**Implemented** (not Verified) and Deployment Status **Not Yet Deployed**.

Sub-issue A #1 (pre-availability read-back) has an **unknown origin** (not the
workflow, tool responses, or documented prompt); the read-once guard is a mitigation
whose effect must be confirmed by conversational testing.

## Regression Requirements

If fixed: preserve the single mandatory pre-booking summary (contract-mandated,
`SYSTEM_CONTRACT.md`); keep "never announce booked unless success=true/booked=true"
and the pricing disclaimer; confirm the spoken phone reads the full 10 digits (no
truncation) with no country code while stored/tool values remain E.164. Verify via
`tests/booking.md` (over-confirmation / over-asking must-never; plus a spoken-phone
check). Prompt-scoped; no workflow/tool regression needed.

## Acceptance Criteria

- Exactly one full appointment read-back (immediately before booking).
- A concise post-booking confirmation (no full re-read of name/vehicle/service/phone).
- No full read-back before the availability check (verify; origin unknown, so this
  is a mitigation to confirm behaviorally).
- Spoken phone = full 10-digit national number, no `+1`, grouped, never truncated;
  stored/tool values remain E.164.
- The Explicit Confirmation contract and success/pricing rules remain intact.
