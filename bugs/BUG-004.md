# BUG-004

**Bug ID:** BUG-004
**Title:** Existing appointment is modified without customer confirmation
**Severity:** High (provisional — confirm during investigation)
**Status:** Open
**Date:** 2026-07-28 (added to tracker). Original report date: Unknown — not recorded in repository.

---

## Description

An existing appointment can be modified without the explicit customer confirmation
the system contract requires for changes to appointments.

## Business Impact

A customer's appointment could be changed without their consent to that specific
change — a direct violation of the Explicit Confirmation contract, eroding trust
and potentially producing scheduling the customer did not agree to.

## Expected Behaviour

- [`SYSTEM_CONTRACT.md`](../SYSTEM_CONTRACT.md) — Explicit Confirmation: the AI
  must obtain explicit customer confirmation before booking, rescheduling, or
  cancelling an appointment.
- [`docs/data-model/customers.md`](../docs/data-model/customers.md): "Never
  overwrite customer information without confirmation."
- Booking/reschedule contracts read back details and wait for a clear yes before
  the workflow executes ([`docs/workflows/rescheduling.md`](../docs/workflows/rescheduling.md),
  [`docs/workflows/booking.md`](../docs/workflows/booking.md)).

## Actual Behaviour

Reported: an existing appointment is modified without explicit confirmation for
that specific change. Not independently reproduced in this documentation pass —
reproduction and confirmation are pending investigation.

## Steps to Reproduce

Unknown — requires investigation. Proposed starting point (not yet executed):
exercise the reschedule path and the repeat-booking path for a phone that already
holds an active appointment, and observe whether the prior appointment is altered
before the caller gives an explicit yes.

## Investigation Status

Not started. Open — investigation required.

## Root Cause

Unknown — requires investigation.

Candidate areas to examine (unconfirmed — starting points only, not a stated
cause):
- The one-active-appointment-per-phone replacement: per `DECISIONS.md`, a new
  booking from a phone with an existing active appointment replaces it — the old
  row is marked `Rebooked` and its calendar event deleted. Whether that
  replacement is gated behind explicit confirmation is the specific question.
- The rescheduling flow and its confirmation gating
  (`docs/workflows/rescheduling.md`, `docs/tools/reschedule_appointment.md`).
- The booking supersede sub-chain referenced in BUG-003.
- Prompt confirmation rules (`production/prompt-v28.txt`) versus workflow gating.

## Acceptance Criteria

- No existing appointment is created, modified, superseded, or cancelled unless
  the customer has given explicit confirmation for that specific change.
- Booking/reschedule/cancel confirmation gates are demonstrated to hold.
- No regression to the one-active-appointment-per-phone or create-before-delete
  decisions (`DECISIONS.md`).

## Engineering Notes

The distinction between a *reschedule* the caller requested and an
*auto-replacement* triggered by a new booking is central: the second can modify
an existing appointment as a side effect. Confirm behavior against the deployed
artifact (`production/workflow-v26.9.json`) before treating any hypothesis as the
cause. Per process, a confirmed root cause does not authorize a fix — findings
must be presented and approved first.

## Regression Requirements

To be defined once the root cause is confirmed. Guards would live in
`tests/reschedule.md` and `tests/booking.md`, asserting no modification before
explicit confirmation.
