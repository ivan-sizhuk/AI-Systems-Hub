# BUG-001

**Bug ID:** BUG-001
**Title:** Post-call workflow halted before Call_Records were written
**Severity:** High
**Status:** Implemented
**Deployment Status:** Not Yet Deployed
**Date:** Unknown — not recorded in repository. Fix implemented in Workflow V27.2. Documented in tracker 2026-07-28.

---

## Description

After a completed call, the post-call processing chain terminated before writing
`Call_Records` and before completing note updates.

## Business Impact

Production observability was defeated: per-call instrumentation and post-call note
updates did not run, so monitoring had no per-call record, even though the
customer-facing call itself completed normally.

## Expected Behaviour

Per [`docs/workflows/post-call-processing.md`](../docs/workflows/post-call-processing.md)
and [`tests/instrumentation.md`](../tests/instrumentation.md): the post-call chain
updates appointment/customer notes and appends exactly one `Call_Records` row per
completed conversation, and instrumentation must not be defeated by an unrelated
post-call step failing.

## Actual Behaviour

The chain halted before `Call_Records` were written. A note update that matched no
row emitted zero items; in n8n a node runs once per input item, so zero items
terminated the entire downstream chain.

## Steps to Reproduce

Recorded in `CHANGELOG.md` (Workflow V27.2); covered by probes I-14/I-15/I-16 in
`tests/instrumentation.md`. Condition: a post-call note update (matched on phone)
finds no matching row — e.g. when the post-call phone value does not match the
stored appointment phone.

## Investigation Status

Complete. Root cause confirmed and recorded in `CHANGELOG.md` and `DECISIONS.md`.

## Root Cause

Three coordinated causes:
1. **Phone-format divergence.** `Parse Post Call Data`'s `formatPhoneForSheet`
   produced bare 10-digit while the booking path, Twilio SMS, and Google Calendar
   use E.164 (`+1…`), so `Update Appointment Notes` (matching on Phone) found no row.
2. **Zero-item halt.** A no-match update emitted zero items, terminating the chain.
3. **Instrumentation coupling.** Call Record writing depended on the note-update
   branch, so a note-update failure prevented instrumentation from running.

## Files Involved

- `production/archive/workflow-v27.2.json` (fix). Nodes changed: `Parse Post Call Data`,
  `Update Appointment Notes`, `Update Customer Notes` (3 nodes, 3 rewires).
- Related decision: `DECISIONS.md` — "Canonical phone format is E.164".

## Implemented Fix

- **Fix 1:** aligned `Parse Post Call Data` to E.164 (not bare 10-digit; the fix
  task specified 10-digit but this was deliberately not adopted — E.164 is the
  established standard and Twilio requires it; see `DECISIONS.md`).
- **Fix 2:** `alwaysOutputData=true` on both note-update nodes so a no-match emits
  an item instead of zero items.
- **Fix 3:** decoupled instrumentation onto its own branch
  (`Build Call Record` → `Append Call Record`), independent of note updates.
- Scope: 3 nodes, 3 rewires. No booking/scheduling/SMS/calendar/prompt node
  changed. `Respond to ElevenLabs` still fires once. Monitoring schema unchanged.

## Acceptance Criteria

- A completed call always appends exactly one `Call_Records` row regardless of
  whether note updates match.
- No-match note updates do not terminate the chain.
- Post-call phone matches the stored phone (E.164).
- No booking/scheduling/SMS/calendar behaviour change.

## Regression Requirements

`tests/instrumentation.md` I-14 (no halt on unmatched notes update), I-15
(instrumentation independent of notes), I-16 (canonical phone format).
