# INV-010

**Investigation for:** [BUG-010](../bugs/BUG-010.md) — Booking confirmation UX: (A) over-confirmation of appointment details, and (B) spoken phone formatting
**Date:** 2026-08-04 · **Investigator:** Engineering (AI session)
**Artifacts examined:** `production/prompt-v28.txt` (current prompt), `production/workflow-v27.5.json` (current dev head), `docs/conversations/booking-conversation.md`, `docs/tools/*`.
**Revision (2026-08-04):** refined the first confirmation's root cause — its origin is **unknown**, not confirmed LLM behavior (repository evidence only rules out workflow / tool responses / documented prompt); and added sub-issue B (spoken phone formatting).

> Investigation only. No workflow, prompt, code, or documentation behavior changed.

## Summary

The booking conversation reads the appointment details back to the caller up to
three times: once **before** checking availability, once as the mandatory
pre-booking summary, and once in the success message. Only the pre-booking summary
is a designed, single confirmation. The evidence attributes #2 and #3 to the
**prompt** (the mandatory summary, intended; and a **verbose success message**,
which re-reads the full summary). The **origin of #1 is currently unknown** — the
repository evidence only establishes that it does not come from the workflow, the
tool responses, or the documented prompt. The n8n workflow and the MCP tool
responses are **not** sources — they return concise messages. This is a
conversational/UX issue, not workflow or tool-response duplication.

## Intended pattern (documented)

`docs/conversations/booking-conversation.md` defines the flow as: … Check
availability → Customer selects → Collect info → **Read appointment summary** →
Customer confirms → Book → **Confirm successful booking**. That is **one** full
summary before booking, then a success confirmation. Step 6 (availability) says
only "present the returned appointment options naturally" — no full read-back.
The expected UX is one pre-booking confirmation and one *concise* post-booking
confirmation.

## Evidence & per-source attribution

**Confirmation #2 (pre-booking summary) — intended, single.**
- `prompt-v28.txt` L192–200: *"MANDATORY CONFIRMATION STEP — never skip: Read back a complete summary and stop: 'Just to confirm — I have you down as [name], [vehicle], for [service], on [date] at [time], and your number is [phone]. Shall I go ahead and book that?' … Never re-confirm an unchanged summary."*
- `book_appointment` tool description reinforces the *same* single summary ("You read back a complete summary to the caller"; STOP AND WAIT). Two instructions, one intended read-back — correct.

**Confirmation #3 (success) — prompt-driven and verbose.**
- `prompt-v28.txt` L208–210 success template restates name + vehicle + service + date/time + phone.
- The workflow's actual tool response is **concise**: `Return Booking Success` → `message: p.message || 'Booked for ${appointmentDate} at ${appointmentTime}.'`; `Prepare Booking Payload` → `'Booked for [date] at [time].'`. So the verbosity is **the prompt's**, not the tool's. (Per `docs/integrations/elevenlabs.md`, the tool `message` is the "reply basis," but the prompt's explicit success template overrides it toward a full re-read.)

**Confirmation #1 (pre-availability read-back) — no instructing component found.**
- The prompt's `get_availability` section (L161+) and the `get_availability` tool description contain **no** instruction to read the full request back before checking availability; the documented Step 6 only "presents options."
- The tool response cannot be the source (it is emitted *after* the check).
- **The origin of the first confirmation is currently unknown.** Based on repository evidence, it does not originate from the workflow, the tool responses, or the documented prompt. It is likely produced by behavior outside the repository (for example, emergent model behavior or ElevenLabs configuration such as agent-level instructions), but **this has not been confirmed** — the repository does not contain the evidence needed to identify the source, and no model/conversation trace or ElevenLabs console configuration was available to this investigation.

**Ruled out:** workflow duplication (single concise message) and tool-response duplication (concise `message`). No dynamic variable restates the summary.

## Answers to the investigation questions

1. **Which component generates each?** #1 → **origin unknown** (ruled out: workflow, tool responses, documented prompt; likely outside-repository behavior — emergent model behavior or ElevenLabs configuration — but unconfirmed); #2 → prompt (+ book_appointment description), intended; #3 → prompt success template (tool response is concise).
2. **Intentional per the docs?** #2 yes (documented, single). #3 is documented as a success confirmation but is **more verbose than the intended concise one**. #1 is **not** documented.
3. **Multiple components instructing duplication?** No — it is **not** several components each emitting a read-back. The prompt instructs two full/near-full restatements by design (#2 and #3); #1 is not instructed by any repository component (origin unknown); the tool description only reinforces the *same* #2.
4. **Timeline:** above.
5. **Classification:** **primarily prompt behavior** (an over-verbose success confirmation), **plus one confirmation (#1) of unknown origin** that is not produced by the workflow, tool responses, or documented prompt. **Not** workflow duplication, **not** tool-response duplication. #2 is expected; the net three-times repetition is a confirmed UX issue.

## Root cause (two sub-issues)

**Sub-issue A — over-confirmation.** The caller hears the full booking details up to
three times because: (a) the **prompt's success message re-reads the entire summary**
(name/vehicle/service/date/phone) rather than giving the intended *concise*
post-booking confirmation; and (b) an **extra read-back occurs before the
availability check (#1) whose origin is unknown** — it is not produced by the
workflow, the tool responses, or the documented prompt (see above), and the prompt
contains no guard against it. The single pre-booking summary (#2) is correct. The
workflow and tool responses are concise and are not contributors.

**Sub-issue B — spoken phone formatting.** When the assistant speaks the phone
number (in the summary #2 and the success message #3), it reads the stored **E.164**
value including the domestic country code — e.g. `+1 437 241 5892` → "one four three
seven …". Evidence: the phone value is E.164 (`Set Data1` `normalizePhone` →
`+1XXXXXXXXXX`; prompt `PHONE NUMBER RULES` L102–115 format as `+1XXXXXXXXXX`); the
summary/success templates read `[phone]` **verbatim** (`prompt-v28.txt` L195, L209);
and the prompt contains **no rule for how to vocalize a phone number**. The stored
format is correct and should stay E.164 (used internally and for SMS) — the issue is
purely how the number is spoken. Expected: speak the complete **10-digit national
number**, dropping the `+1` country code, grouped (e.g., "437-241-5892" / "four
three seven, two four one, five eight nine two"), reading the **entire** number
(never truncated, never only the last four digits) so the caller can catch an error
anywhere in it.

## Recommended minimal fix (recommendation only — do not implement)

Prompt-only, no workflow/tool change:

1. **Make the success confirmation concise.** Change the `book_appointment` success
   template (`prompt-v28.txt` L208–210) so it confirms completion + date/time and
   the pricing disclaimer **without** re-reading name/vehicle/service/phone (those
   were just confirmed in #2). This aligns with the concise tool `message` and the
   intended UX.
2. **Guard against the pre-availability read-back (#1).** Add one line (extending the
   existing "Never re-confirm an unchanged summary" principle) stating that the
   complete summary is read back **exactly once**, immediately before booking — not
   before `get_availability`. Because #1's origin is unknown (see Root cause,
   Sub-issue A), a prompt guard is a **mitigation** whose effectiveness must be
   verified; if it persists, the source is likely outside the repository (model
   behavior or ElevenLabs agent configuration) and should be investigated there.
3. **Add a phone-vocalization rule (Sub-issue B).** In the `PHONE NUMBER RULES`
   section and the two spoken templates (L195, L209), instruct: when *speaking* the
   phone to the caller, read the full 10-digit national number without the `+1`
   country code, grouped (e.g., "437-241-5892"); never truncate or read only the
   last four digits. Storage and tool inputs remain E.164 (`+1XXXXXXXXXX`) —
   unchanged.

Each is a minimal prompt edit; together they would be one prompt-version bump, code
review, and the conversational regression in `tests/booking.md` (must-never:
over-asking / over-confirming; and a new check on spoken phone formatting). No
workflow, tool, or schema change.

## Risks / scope

Prompt-scoped and low-risk. Regression must confirm the single pre-booking summary
(#2) is preserved (it is contract-mandated — `SYSTEM_CONTRACT.md` Explicit
Confirmation), that the success message still meets the "never announce booked
unless success=true/booked=true" and pricing-disclaimer requirements, and that the
spoken phone reads as the full 10 digits (no truncation). #1's origin is unknown
(not attributable to the repository), so the guard *may reduce but not eliminate*
it; verify by conversational testing, and if it persists, investigate outside the
repository (model behavior / ElevenLabs configuration).

## Stop

Root cause confirmed; sources attributed; minimal fix recommended. **Stopping — no
