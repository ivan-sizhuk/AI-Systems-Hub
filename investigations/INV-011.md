# INV-011

**Investigation for:** [BUG-011](../bugs/BUG-011.md) — Call does not hang up after the goodbye (silence path)
**Date:** 2026-08-07 · **Investigator:** Engineering (AI session)
**Artifacts examined:** `production/workflow-v26.9.json` (production of record) and `production/workflow-v27.5.json` (dev head); `production/prompt-v28.txt` (production prompt) and `production/prompt-v29.txt` (dev prompt); `docs/tools/end_call.md`, `tests/tool-behavior.md`, `tests/edge-cases.md`, `docs/integrations/*`.

> Investigation only. No workflow, prompt, code, or documentation behavior changed.

---

## Summary

When the caller is silent, the assistant delivers the two-step silence script and the
farewell ("…Feel free to call us back whenever you're ready. Have a great day!"), then
is instructed to call `end_call`. From repository evidence it is **confirmed** that: the
end-call branch only disconnects the Twilio call when it resolves a valid Twilio **call
SID**; when it cannot, the workflow performs **no hangup** and returns `end_call=true`
with a note that the provider will time the call out; the **prompt never passes
`system__call_sid`** to `end_call`, although the tool contract and test spec require it;
and **both** terminal nodes return `success=true` regardless of outcome. It is **inferred**
(not confirmed from the repository) that the "provider timeout" does not actually
disconnect a live, silent call and that this is what produces the reported symptom — that
depends on Twilio/ElevenLabs runtime behavior, which the repository does not capture.

So the repository confirms an **architectural risk** (a termination path that can return
success while leaving the call connected); it does **not** by itself confirm the
production failure mechanism for the reported call. See Required evidence below.

The confirmed architectural facts are present identically in production (v26.9 /
prompt-v28) and the dev head (v27.5 / prompt-v29).

> Inference; added a Required-evidence section and an explicit statement of the
> architecture-risk-vs-production-mechanism limit.

## Complete call-termination sequence (as built)

```
Caller goes silent
  ↓  (prompt) Step 1: "Are you still there?"  → wait
  ↓  (prompt) Step 2: "...Feel free to call us back whenever you're ready. Have a great day!"
  ↓  (prompt) "IMMEDIATELY call end_call with reason 'caller_silent'"  (reason only; NO system__call_sid)
  ↓  ElevenLabs invokes the end_call MCP tool
  ↓  end_call (toolWorkflow, action=end_call) → When Executed by Another Workflow → Business Config → Switch
  ↓  Switch(action=end_call) → Read Sessions For End Call → End Call Context
        End Call Context resolves callSid: (1) Sessions sheet CA-row → (2) static data (epoch-gated) → (3) trigger.call_sid / trigger.system__call_sid
  ↓  Valid Call SID?  (isValidSid = /^CA[a-f0-9]{32}$/i)
      ├─ TRUE  → Wait Before Hangup (3s) → Twilio - End Call (POST .../Calls/{sid}.json  Status=completed)
      │             → Twilio - Redirect to Hangup TwiML (POST Url=/hangup) → Return End Call Success (success=true, end_call=true)
      └─ FALSE → Return No SID Error (success=true, end_call=true, note "Twilio will time out the call")  ← NO hangup performed
  ↓  Twilio ends the call (only on the TRUE path) → media stream closes → ElevenLabs conversation ends
```

## Investigation questions — answers

- **Which component decides to say the goodbye?** The **prompt** (SILENCE HANDLING, prompt-v28/29 L303–309).
- **Which component actually ends the call?** The **n8n End Call branch → Twilio REST API** (`Twilio - End Call`, `POST .../Calls/{sid}.json Status=completed`, plus `Twilio - Redirect to Hangup TwiML`). ElevenLabs ends only as a *consequence* of Twilio closing the media stream.
- **Is the assistant expected to invoke `end_call`?** **Yes** — prompt L316–322 "Always say farewell first, then call end_call immediately. Never skip end_call."
- **Should ElevenLabs auto-terminate?** No evidence it self-terminates; termination is driven by the Twilio hangup. Whether ElevenLabs also ends on `end_call=true` is **Unknown** (config outside the repo).
- **Is Twilio expected to hang up?** **Yes** — via the REST `Status=completed` call (and the redirect-to-hangup TwiML). Requires a valid call SID + account SID + credentials.
- **Is n8n expected to act after the goodbye?** **Yes** — resolve the SID and call Twilio to disconnect.

## Evidence

Confirmed (C), Inferred (I), Unknown (U).

- **C1 — Prompt instructs the farewell + end_call.** prompt-v28/29 L305–309: Step 1 "Are you still there?"; Step 2 the exact goodbye then *"IMMEDIATELY call end_call with reason 'caller_silent'."* L322: *"Always say farewell first, then call end_call immediately. Never skip end_call."* The reported phrase matches Step 2. (So this is **not** a "prompt never instructs" case.)
- **C2 — Prompt omits `system__call_sid`.** `system__call_sid` does **not** appear anywhere in prompt-v28 or prompt-v29; the model is told to pass `reason` only. Yet `docs/tools/end_call.md` lists `system__call_sid` as **Required** ("passed exactly as received") and `tests/tool-behavior.md` L93 states required inputs are *"reason; system__call_sid passed as received."* → **confirmed prompt/contract mismatch.**
- **C3 — Hangup is SID-gated.** `End Call Context` computes `isValidSid = /^CA[a-f0-9]{32}$/i.test(callSid)`, `canEnd = isValidSid`; `Valid Call SID?` routes TRUE→hangup, FALSE→`Return No SID Error`.
- **C4 — Both Twilio hangups need the resolved SID.** `Twilio - End Call` and `Twilio - Redirect to Hangup TwiML` both build `.../Calls/{End Call Context.callSid}.json`. No SID ⇒ neither runs.
- **C5 — No-SID path performs no hangup.** `Return No SID Error`: returns `success:true, end_call:true, note:"SID not available — Twilio will time out the call."` — explicitly no hangup.
- **C6 — Success is always reported.** Both `Return End Call Success` and `Return No SID Error` return `success:true, end_call:true`. The AI stops talking regardless of whether the call actually ended.
- **C7 — The "provider timeout" fallback is the documented design.** `tests/edge-cases.md` L111: *"end_call without a stored call SID: the provider times the call out; AI behavior is unchanged."* `tests/tool-behavior.md` L95: *"no SID → provider timeout note."* So no-hangup-on-no-SID is intended, relying on Twilio to time the call out.
- **C8 — call SID sources depend on init / injection.** End Call Context's SID comes from the Sessions sheet or static data (both written only by the `/setVar` initialization branch: `Set1 → Save Call SID to Static Data → Store Phone in Static Data`), or from `trigger.system__call_sid` — which the prompt does not pass (C2).
- **C9 — Present in both versions.** End Call branch nodes are byte-identical in v26.9 and v27.5; the silence/end_call prompt section is identical in v28 and v29.
- **I1 — Reported symptom ⇒ hangup did not execute.** "Goodbye said, call never ends" is consistent with the FALSE (no-SID) path (no hangup) or a failed Twilio hangup request. Given C2, the direct `trigger.system__call_sid` source is likely empty, leaving only the init-dependent Sessions/static SID.
- **I2 — The "provider timeout" assumption is likely ineffective.** Twilio does not automatically disconnect a live call because of caller silence or because the AI stopped speaking; without an explicit hangup (REST `Status=completed` / `<Hangup/>` TwiML) or an ElevenLabs conversation-end that closes the stream, the call persists. So on the no-SID path the call would not reliably end — matching the report.
- **U1 — Whether a valid SID was resolved in the reported call.** Requires the n8n execution log (not available).
- **U2 — Whether the Twilio hangup request(s) failed** (credentials/account SID/SID format/timeout). Requires the execution log / Twilio logs.
- **U3 — Whether ElevenLabs auto-injects `system__call_sid`** into the tool call despite the prompt not passing it. Requires the ElevenLabs agent/tool configuration (outside the repo).
- **U4 — Whether ElevenLabs self-terminates on `end_call=true`** or relies solely on the Twilio media-stream close. Outside the repo.

## Root cause

**Confirmed — architectural (repository evidence only):**
- (a) the prompt calls `end_call` with `reason` only and **never passes
  `system__call_sid`** (violating the tool contract / test spec, C2), removing the most
  direct call-SID source;
- (b) when no call SID is resolved, the workflow performs **no hangup** and returns
  `end_call=true` with a "provider will time the call out" note (C5, C7); and
- (c) **both** terminal responses report `success=true` regardless of the telephony
  outcome (C6), so a non-hangup is not surfaced as a failure.

Together these are a confirmed **architectural risk**: a termination path that can report
success while performing no disconnect.

**Inferred (depends on runtime behavior — NOT confirmed from the repository):**
- that the "provider timeout" does not actually disconnect a live, silent Twilio call
  (I2), and therefore that the no-SID path (or a failed Twilio hangup) is what produces
  the reported "call never ends" symptom (I1). These depend on Twilio/ElevenLabs runtime
  behavior the repository does not capture.

**Unknown — requires additional evidence (precise production failure mechanism):** which
path actually fired in the reported call — no-SID vs a failed Twilio hangup vs an
ElevenLabs non-invocation — and whether the SID resolved. Not determinable from the
repository alone; see Required evidence below.

**Bottom line:** the repository **confirms an architectural risk** but **cannot yet
confirm the production failure mechanism** for the reported call.

## Components involved

- **Prompt** (ElevenLabs system prompt): decides the farewell and the `end_call` invocation; omits `system__call_sid`.
- **ElevenLabs**: invokes the `end_call` MCP tool; may or may not inject `system__call_sid` / self-terminate (Unknown).
- **MCP**: transports the tool call into n8n.
- **n8n workflow** (End Call branch): `end_call`, `When Executed by Another Workflow`, `Business Config`, `Switch`, `Read Sessions For End Call`, `End Call Context`, `Valid Call SID?`, `Wait Before Hangup`, `Twilio - End Call`, `Twilio - Redirect to Hangup TwiML`, `TwiML Hangup Webhook`, `Return End Call Success`, `Return No SID Error`.
- **Twilio**: the REST hangup (`Status=completed`) and redirect-to-hangup TwiML actually disconnect the call.
- **Sessions sheet / n8n static data**: hold the `call_sid` written at call start by the `/setVar` init branch.

## Files involved

- `production/prompt-v28.txt` (prod) and `production/prompt-v29.txt` (dev): SILENCE HANDLING (~L303–309) and end_call rules (~L316–322); both omit `system__call_sid`.
- `production/workflow-v26.9.json` (prod of record) and `production/workflow-v27.5.json` (dev head): the End Call branch (identical in both).
- `docs/tools/end_call.md`: contract (system__call_sid Required; "no SID → provider timeout").
- `tests/tool-behavior.md` (L89–95) and `tests/edge-cases.md` (L98–116): documented end_call expectations, incl. the "provider times the call out" assumption.

## Recommended implementation options (NOT implemented)

1. **Prompt (smallest):** instruct the model to pass `system__call_sid` (the ElevenLabs system variable) to `end_call`, per the tool contract — restoring the direct SID source so the hangup can run even if the Sessions/static sources are empty. *Depends on ElevenLabs actually providing `system__call_sid` (U3) — verify in the console.*
2. **Workflow — fail safe on no SID:** replace the "provider timeout" assumption with an active termination. Options: if no SID, attempt to end via the ElevenLabs conversation-end signal and/or surface a real failure/alert instead of `success=true`; or capture the SID more robustly (see 3). At minimum, add error handling/verification on the two Twilio hangup requests (retry / confirm `completed`), since a failed hangup currently still returns success.
3. **Architecture — reliable SID at call start:** ensure `call_sid` is always captured and available to the End Call branch (harden the `/setVar` init writes to Sessions/static data), removing the dependency on model-passed or injected SIDs.
4. **Verify the platform contract:** confirm (a) ElevenLabs injects/permits `system__call_sid`, (b) whether ElevenLabs ends the conversation on `end_call=true` or only via the Twilio stream close, and (c) that the Twilio REST `Status=completed` / redirect-TwiML actually disconnect in this deployment (account SID + credentials).

The smallest change is option 1, but on its own it only helps if ElevenLabs supplies `system__call_sid`; the "call never ends" symptom on the **no-SID** path (option 2/3) is the deeper issue and likely needs a workflow/architecture change plus a live verification (option 4).

## Risk assessment

- **Blast radius:** `end_call` runs at the end of *every* call; changes risk either (a) ending calls prematurely (cutting off callers) or (b) continuing to leave calls open. It shares Twilio-call-control mechanisms (redirect/TwiML) with `human_handoff` — avoid interfering with transfer.
- **External dependencies:** the fix's effectiveness depends on ElevenLabs configuration (system variables / conversation-end) and Twilio credentials/account SID — partly outside the repo, so a **live call test is required** to verify actual disconnect.
- **Severity:** customer-facing and billing-relevant (calls staying connected consume telephony minutes and leave the caller on a dead line), but not data-corrupting. Suggested severity **High**.
- **Regression scope (for any future fix):** silence two-step → actual disconnect; natural-conclusion / abusive / robocall → disconnect; no-stored-SID scenario → verify the call actually ends (not just `success=true`); confirm `human_handoff` transfer is unaffected; and a live Twilio verification that the call truly hangs up.
