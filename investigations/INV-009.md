## Summary

`Return Customer Lookup` **does** implement session-first precedence, but the test
it uses to decide "is there a valid session phone" is unreliable. It accepts the
stored session phone only if the session's `stored_at` timestamp is less than two
hours old, and it computes that age by parsing a **Toronto wall-clock string that
carries no timezone offset** with `new Date(...)`, then comparing to `Date.now()`.
When the n8n execution timezone is not `America/Toronto` (n8n's default is UTC, and
the workflow sets no timezone), the parsed instant is offset by the Toronto UTC
offset (~4–5 h), so a **freshly stored** session phone is judged older than two
hours and discarded. The code then falls back to the parent trigger's phone — in
the reported call the placeholder `+16135551212` — which normalizes to
`6135551212`, exactly the observed `searchedPhone`.

## Evidence

### E1 — The phone-resolution logic (node `Return Customer Lookup`, type `code`)

The relevant excerpt of its `jsCode`:

```js
function normPhone(v) {
  const d = (v || '').toString().replace(/[^\d]/g, '');
  if (d.length === 11 && d.startsWith('1')) return d.slice(1);
  return d;
}
const trigger = $('When Executed by Another Workflow').first().json || {};
...
let phone = '';
try {
  const sessionRows = $('Read Session Phone').all().map(r => r.json || {}).filter(r => r.caller_phone);
  if (sessionRows.length > 0) {
    sessionRows.sort((a, b) => new Date(b.stored_at || 0) - new Date(a.stored_at || 0));
    const mostRecent = sessionRows[0];
    const storedMs = new Date(mostRecent.stored_at || 0).getTime();
    const ageMs = Date.now() - storedMs;
    if (ageMs < 7200000) {           // 2 hours
      phone = normPhone(mostRecent.caller_phone);
    }
  }
} catch(e) {}
if (!phone) phone = normPhone(trigger.caller_phone || trigger.caller_id || trigger.phone || '');
```

Precedence is session-first, parent-trigger-second — matching the documented
intent — **but** the session branch is gated on `ageMs < 7200000`.

### E2 — How `stored_at` is written (node `Store Phone in Static Data`, Sessions append)

```
stored_at = {{ $now.setZone('America/Toronto').toFormat('ccc, LLL d, yyyy h:mm a') }}
```

This produces strings like `"Thu, Jul 30, 2026, 10:30 AM"` — a Toronto wall-clock
time **with no UTC offset or zone**. (`caller_phone` for the session is
`{{ $('Set1').first().json.phone }}`, and `Set1.phone` is captured from the
inbound webhook body: `body.caller_id || body.caller_phone || body.customerPhone
|| query.phone`.)

### E3 — The workflow sets no timezone

`workflow-v26.9.json` `settings` = `{"executionOrder": "v1", "availableInMCP": false}`.
There is **no `settings.timezone`**, so the JavaScript `new Date(...)` parse in
`Return Customer Lookup` uses the n8n process timezone (env `TZ` / `GENERIC_TIMEZONE`),
which defaults to UTC.

### E4 — Empirical reproduction of the age skew

Storing "now" as a Toronto wall-clock string (per E2) and re-parsing it with
`new Date(...)` under process `TZ=UTC` (per E3) gives:

```
stored_at string: "Thu, Jul 30, 2026, 10:30 AM"
ageMs: 14412993  → 4.00 hours  → passes <2h gate: false
```

A phone stored seconds ago is treated as 4 hours old. The 4 h equals Toronto's
current UTC−4 (EDT) offset. Any daytime session therefore fails the 2-hour gate.

### E5 — The fallback value matches the observed evidence exactly

`normPhone('+16135551212')` → strip non-digits → `16135551212` → 11 digits
starting with `1` → drop leading `1` → **`6135551212`**. This is precisely the
`searchedPhone = 6135551212` recorded in BUG-009, confirming the fallback branch
(`trigger.phone`) executed rather than the session branch. (For comparison, the
session phone `14372415892` would have normalized to `4372415892`.)

### E6 — The parent trigger carries `phone`

The trigger `When Executed by Another Workflow` (`executeWorkflowTrigger`) declares
a `phone` input (among many). In the reported call the parent passed the
placeholder `+16135551212`, which is what `trigger.phone` returns to the fallback.

## Node analysis

- **`Return Customer Lookup`** (code) — proximate location of the defect. Resolves
  the lookup phone; the `ageMs < 7200000` gate on a timezone-ambiguous `stored_at`
  wrongly rejects the current session phone and falls through to `trigger.phone`.
- **`Store Phone in Static Data`** (Google Sheets, Sessions append) — writes
  `stored_at` as Toronto wall-clock without offset (the format that cannot be
  compared safely downstream). On the webhook path, not the lookup path.
- **`Read Session Phone`** (Google Sheets, Sessions read) — reads the **entire**
  Sessions sheet (`options: {}`, no filter). The code then picks the globally
  most-recent row within 2 h; it is **not scoped to the current call's**
  `call_sid`/`conversation_id`. Secondary weakness (see Risks).
- **`When Executed by Another Workflow`** (trigger) — supplies `trigger.phone`, the
  parent-passed value used by the fallback.

## Confirmed root cause

**The session-phone freshness gate in `Return Customer Lookup` rejects a valid,
current session phone because `stored_at` is written as a Toronto wall-clock string
with no timezone offset (`Store Phone in Static Data`) and parsed with `new Date()`
in the process timezone (no `settings.timezone`; n8n defaults to UTC). The
resulting age is inflated by the Toronto UTC offset (~4 h), exceeding the 2-hour
window, so the code falls back to the parent trigger's `phone` — the placeholder
`+16135551212` → `searchedPhone = 6135551212`.**

Confidence: the defect and mechanism are confirmed from the repository (E1–E6).
The one value not visible in the repository is the production n8n instance
timezone; the observed `searchedPhone` (E5) proves the fallback branch executed
while a session phone existed, and the only code path that produces that outcome is
the failed freshness gate. A production execution log showing the computed `ageMs`,
or the instance `TZ`/`GENERIC_TIMEZONE`, would remove the last environmental
unknown but is not required to establish the defect.

## Rejected hypotheses

- **"`stored_at` is unparseable, so `new Date` returns Invalid Date."** Rejected:
  `new Date("Thu, Jul 30, 2026, 10:30 AM")` parses to a valid instant in Node 22
  (tested). The problem is the *timezone* of that instant, not a parse failure.
- **"The session was genuinely older than 2 hours."** Rejected as the general
  cause: the skew reproduces for a session stored seconds earlier (E4), and
  BUG-009 frames the session as the active/current one.
- **"No session row existed / `caller_phone` was empty, so it fell back."**
  Rejected as the reported cause: BUG-009's evidence records an active session
  phone (`14372415892`); the store node writes `caller_phone` + `stored_at`. (If a
  row were genuinely absent the same fallback would occur, but that is not the
  reported scenario.)
- **"Phone normalization dropped/rewrote the session number."** Rejected:
  `normPhone` handles both numbers correctly (`14372415892`→`4372415892`,
  `+16135551212`→`6135551212`); the wrong number was *selected*, not mis-normalized.

## Risks

- **Systemic pattern, not a single node.** The same `stored_at` + `7200000` gate +
  `new Date(stored_at)` construction appears in multiple code nodes —
  `Code2`, `Set Data1`, `Code4`, `Set Data2`, `Cancel Appointment Context`,
  `End Call Context`, `Return Appointment Lookup` (and `Filter Old Sessions` /
  `Save Call SID to Static Data` use `stored_at` differently). This is consistent
  with BUG-009's stated impact on **rescheduling and cancellation**, not just
  customer lookup. A fix limited to `Return Customer Lookup` would leave the same
  timezone fragility in the reschedule/cancel/end-call/appointment-lookup paths.
- **Unscoped session selection (secondary).** Because `Read Session Phone` is
  unfiltered and the code takes the most-recent session across *all* rows,
  concurrent calls could select another caller's phone even after the timezone
  issue is fixed. Any fix should scope selection to the current call's `call_sid`
  / `conversation_id`.
- **Sessions schema/format change.** Correcting the timestamp (ISO-with-offset or
  epoch-ms) changes what `Store Phone in Static Data` writes; existing historical
  rows in the Sessions sheet use the old format, so the read/compare logic must
  tolerate both during transition.
- **Contract sensitivity.** Changes touch the customer-identification entry point
  used before booking/reschedule/cancel/lookup (`docs/workflows/customer-lookup.md`).
  Regressions here affect every downstream flow, so regression must be broad.

## Recommended implementation (recommendation only — NOT authorization)

A robust fix has two parts:

1. **Make the freshness comparison timezone-safe.** Store the session timestamp in
   an unambiguous form and compare numerically. Preferred: add/emit an epoch-ms
   value (e.g. `$now.toMillis()`), or write ISO-8601 with offset
   (`$now.toUTC().toISO()` / `$now.toISO()`), and compute `ageMs` from that. This
   removes the process-timezone dependency entirely. Retain tolerance for the
   legacy `stored_at` string during a transition window.
2. **Scope session selection to the current call.** Prefer the Sessions row whose
   `call_sid` (and/or `conversation_id`) matches the current trigger, rather than
   "most recent across all sessions." This implements BUG-009's documented priority
   precisely: (1) current active-session phone → (2) parent trigger phone only if
   no valid session phone exists → (3) ask the caller.

Consistency: apply the same timezone-safe comparison to the sibling nodes listed
under Risks so reschedule/cancel/end-call/appointment-lookup do not retain the
defect.

Placeholder rejection (an acceptance criterion) is best achieved *structurally* —
by correctly preferring the real session phone — rather than by hardcoding specific
test numbers, which is brittle.

Smallest change that resolves the reported evidence: part 1 on `Return Customer
Lookup` + `Store Phone in Static Data`. Recommended complete change: parts 1 and 2,
extended to the sibling nodes. Final scope is a decision for the approval step.

### Likely files/nodes in a future change (for planning only)

- `Store Phone in Static Data` (Sessions append) — timestamp format.
- `Read Session Phone` (Sessions read) — optionally add a `call_sid` filter (or

- Sibling session-freshness nodes (consistency): `Code2`, `Set Data1`, `Code4`,
  `Set Data2`, `Cancel Appointment Context`, `End Call Context`,
  `Return Appointment Lookup`.

### Regression scope a fix would require

- Return customer lookup: valid current session; expired/absent session; fallback
  to parent only when no session phone; placeholder rejection.
- Timezone independence: correct behavior with the instance in UTC and in
  America/Toronto.
- Reschedule and cancellation identify the returning customer correctly.
- Concurrency: two overlapping sessions do not cross phones.
- No change to booking/new-customer, reminders, SMS, or post-call analytics.
