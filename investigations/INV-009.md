# INV-009

**Investigation for:** [BUG-009](../bugs/BUG-009.md) — Return Customer Lookup ignores the active session phone and falls back to the parent workflow placeholder phone
**Date:** 2026-07-31
**Investigator:** Engineering Manager (AI session)
**Process:** Conducted per [`AI_ENGINEERING_RULES.md`](../AI_ENGINEERING_RULES.md) and [`investigations/README.md`](README.md). This is the project's first investigation using the documented process.
**Primary artifact:** `production/workflow-v27.4.json` — the **current development workflow** (`production/README.md` → Version Reference). Historical comparison against the production of record (`workflow-v26.9.json`) is used only where noted.

> Scope: analysis only. No workflow, node, code, sheet, or integration was
> modified. No fix is implemented (Rules 9–10 — a confirmed root cause does not
> authorize implementation).

---

## Result at a glance

- **Reproduced:** Yes — deterministically, from repository evidence.
- **Root cause:** Confirmed. **Workflow logic** — `Return Customer Lookup` parses
  the session `stored_at` timestamp with timezone-naive `new Date()`; when the n8n
  execution timezone is not `America/Toronto` (n8n default is UTC), a *fresh*
  session is mis-aged by the Toronto UTC offset (~4 h), fails the 2-hour freshness
  gate, and the code falls back to the parent trigger phone.
- **Proof:** The same repository parses the identical `stored_at` field correctly
  elsewhere (`Filter Old Sessions`, zone-aware luxon), so `new Date()` is a genuine
  defect, not an environment quirk.

### E1 — `Return Customer Lookup` (type `code`) — phone resolution

```js
function normPhone(v) {
  const d = (v || '').toString().replace(/[^\d]/g, '');
  if (d.length === 11 && d.startsWith('1')) return d.slice(1);
  return d;
}
const trigger = $('When Executed by Another Workflow').first().json || {};
...
let phone = '';
try {
  const sessionRows = $('Read Session Phone').all().map(r => r.json || {}).filter(r => r.caller_phone);
  if (sessionRows.length > 0) {
    sessionRows.sort((a, b) => new Date(b.stored_at || 0) - new Date(a.stored_at || 0));   // naive parse (sort)
    const mostRecent = sessionRows[0];
    const storedMs = new Date(mostRecent.stored_at || 0).getTime();                        // naive parse (age)
    const ageMs = Date.now() - storedMs;
    if (ageMs < 7200000) { phone = normPhone(mostRecent.caller_phone); }                    // 2-hour gate
  }
} catch(e) {}
if (!phone) phone = normPhone(trigger.caller_phone || trigger.caller_id || trigger.phone || '');  // fallback
...
// match against Customers by normPhone(Phone) === phone; returns { searchedPhone: phone, ... }
```

## Investigation questions (answered from evidence)

1. **How is the session phone stored?** At call start, `Set1` captures the phone
   from the webhook body; `Store Phone in Static Data` **appends** a `Sessions`
   row (`call_sid`, `conversation_id`, `caller_phone`, `stored_at`). A parallel
   `Save Call SID to Static Data` also writes `call_sid`/`caller_phone`/`stored_at`
   (epoch ms) to n8n **static data**, used by `end_call` — not by lookup.
2. **How is the session phone retrieved?** `Read Session Phone` reads the **entire
   Sessions sheet** (no filter); `Return Customer Lookup` keeps rows where
   `caller_phone` is truthy.
3. **How is the session selected?** In code: sort all rows by `stored_at`
   descending, take `[0]`. **Not scoped** to the current `call_sid`/`conversation_id`.
4. **How is the newest session determined?** By `new Date(b.stored_at) - new
   Date(a.stored_at)` — a **timezone-naive** parse of the Toronto wall-clock string.
5. **When does fallback to the parent workflow occur?** When `phone` is still empty
   after the session branch — i.e. the most-recent session failed the
   `ageMs < 7200000` gate (or no row had `caller_phone`). Then
   `phone = normPhone(trigger.caller_phone || trigger.caller_id || trigger.phone)`.
6. **Under what conditions can the parent overwrite the session phone?** The parent
   never overwrites the stored row; the **fallback selects** the parent phone
   whenever the session branch fails to set `phone`. The dominant trigger is the
   timezone-skewed freshness gate (below); also a genuinely >2h-old row, or a row
   lacking `caller_phone`.
7. **Can stale session data be selected?** Yes in principle — selection is
   "most-recent across all rows within 2h," unscoped to the current call. Under the
   timezone defect the opposite also happens: **fresh** sessions are wrongly judged
   stale and rejected.
8. **Can multiple sessions exist simultaneously?** Yes. `Store Phone` **appends**
   (no dedupe); `Read Session Phone` reads all rows. Overlapping calls coexist
   until `Filter Old Sessions`/`Delete Old Sessions` prune rows >2h.
9. **How is `stored_at` validated?** In `Return Customer Lookup`: **not correctly**
   — `new Date(stored_at || 0)`; a missing/invalid value becomes `new Date(0)`
   (1970) → huge age → rejected. In `Filter Old Sessions`: **correctly** — luxon
   `fromISO` then `fromFormat(..., { zone: 'America/Toronto' })`.
10. **Is the fallback logic functioning as designed?** The fallback **code** runs
    exactly as written (session-first, else trigger). But the **validity test** it
    depends on is defective, so the fallback fires when a valid session phone
    exists. The *design intent* ("use parent only if no valid session phone") is
    **not** achieved.
11. **Is the bug caused by workflow logic / data / timing / normalization / session
    lifecycle / other?** **Workflow logic** — a timezone-naive timestamp parse in
    `Return Customer Lookup`. Not data (the session row is correct), not
    normalization (`normPhone` is correct for both numbers), not timing (reproduces
    for a session stored seconds earlier), not session lifecycle (the row is
    present and fresh). A secondary **workflow-logic** weakness is the unscoped
    session selection.

## Reproduction

**Reproduced: yes**, deterministically, using repository evidence. Simulating the
two parsers node-accurately on a freshly written `stored_at` under the n8n-default
process timezone (`TZ=UTC`):

```
stored_at written:  "Fri, Jul 31, 2026 4:57 PM"   (Store Phone → Toronto wall-clock)
[Return Customer Lookup]  new Date(stored_at)   → age 4.01 h  → passes <2h gate: FALSE
[Filter Old Sessions]     luxon zone-aware      → age 0.01 h  → passes <2h gate: TRUE
```

A session stored **seconds ago** is seen as **4 hours old** by `Return Customer
Lookup`, so its phone is discarded and the code falls back to the parent trigger
phone. `normPhone('+16135551212')` → `6135551212`, exactly the reported
`searchedPhone`. The correct session phone `14372415892` would have produced
`4372415892`.

**Condition:** the bug manifests whenever the n8n execution timezone ≠
`America/Toronto`. n8n's default is UTC, the workflow sets no timezone (E5), and
the repo's own `Filter Old Sessions` comment (E6) shows the environment is not
assumed to be Toronto. Under UTC the ~4 h skew exceeds the 2 h window for **every**
daytime session, so the fallback effectively always fires.

**Not fully observable from the repository:** the production instance's actual
`TZ`/`GENERIC_TIMEZONE`. It is not required to establish the defect — the reported
`searchedPhone` (E8) proves the fallback executed while a session phone existed,
and the only code path producing that is the failed freshness gate. A production
execution log showing the computed `ageMs` would close this last detail.

## Confirmed root cause

**Workflow logic defect in `Return Customer Lookup` (`production/workflow-v27.4.json`).**
It parses the Toronto-wall-clock `stored_at` with timezone-naive `new Date()` for
both the newest-session sort and the 2-hour freshness gate. When the n8n execution
timezone is not `America/Toronto` (default UTC), the computed age is inflated by the
Toronto UTC offset (~4 h), exceeding the 2-hour window, so a valid current session
phone is rejected as stale and the code falls back to the parent trigger phone
(`trigger.caller_phone`/`caller_id`/`phone`) — the placeholder `+16135551212` →
`searchedPhone = 6135551212` in the reported call.

This is **proven** to be a code defect (not an environmental accident) by E6: the
same repository parses the identical `stored_at` field correctly, with zone-aware
luxon, in `Filter Old Sessions`.

**Contributing (secondary) weakness:** `Read Session Phone` is unfiltered and the
selection is "most-recent across all sessions," not scoped to the current call's
`call_sid`/`conversation_id`. Even with the timezone bug fixed, this leaves a
concurrency risk of selecting another caller's session.

Category (Q11): **workflow logic.**

## Rejected hypotheses

- **`stored_at` is unparseable → Invalid Date.** Rejected: `new Date("Fri, Jul 31,
  2026 4:57 PM")` parses to a valid instant. The problem is the *timezone* of that
  instant, not a parse failure.
- **Session genuinely older than 2 hours.** Rejected as the reported cause: the
  skew reproduces for a session stored seconds earlier.
- **Phone normalization corrupted the number.** Rejected: `normPhone` maps both
  numbers correctly (`14372415892`→`4372415892`, `+16135551212`→`6135551212`); the
  wrong number was *selected*, not mis-normalized.
- **Parent workflow overwrote the Sessions row.** Rejected: no node updates the
  session row with the parent phone; `Store Phone` appends the real captured phone,
  and the parent value enters only via the code fallback.
- **Data/timing/session-lifecycle.** Rejected as the *primary* cause: the row is
  present, fresh, and correctly written; the defect is the parse.

## Risks (if a fix were later implemented)

- **Affected workflow:** `workflow-v27.4.json` (current development head). Verified
  the `Return Customer Lookup` code and `stored_at` write are **byte-identical** in
  the production of record `workflow-v26.9.json`, so the defect exists in both.
- **Affected nodes:** `Return Customer Lookup` (proximate). The identical naive
  `new Date(stored_at)` + 2h pattern is present in **sibling nodes**: `Code2`,
  `Set Data1`, `Code4`, `Set Data2`, `Cancel Appointment Context`,
  `End Call Context`, and `Return Appointment Lookup` (2h gate). This is consistent
  with BUG-009's stated impact on **rescheduling and cancellation**; a fix scoped
  only to `Return Customer Lookup` would leave the same fragility elsewhere.
  `Store Phone in Static Data` and `Read Session Phone` are involved for the
  secondary weakness.
- **Affected Google Sheets:** `Sessions` (read/write of `caller_phone`,
  `stored_at`) and `Customers` (the match). A parse-only fix needs **no schema
  change**; a "store epoch ms" approach would **add a column** to `Sessions`.
- **Affected integrations:** **ElevenLabs** (the `lookup_customer` result drives the
  agent's customer-identification behavior) and indirectly **Twilio** (the
  `caller_phone` source). No integration contract change is required for a
  timezone-safe parse.
- **Regression risks:** customer identification is the **entry point** before
  booking, rescheduling, cancellation, and appointment lookup, so a change here has
  broad blast radius. Regression must cover: valid current session; expired
  session; missing session; fallback-to-parent **only** when no valid session
  phone exists; placeholder/test-number rejection; concurrency (multiple
  simultaneous sessions); **timezone independence** (instance in UTC *and* in
  America/Toronto); and no change to new-customer/booking, reminders, SMS, or
  post-call analytics. Any fix must respect `SYSTEM_CONTRACT.md` and `DECISIONS.md`
  (E.164/Appointments-record-as-source-of-truth) and preserve backwards
  compatibility (Rule 13).

## Recommended implementation (recommendation only — NOT authorization; Rules 9–10)

Smallest change that resolves the reported evidence: parse `stored_at`
timezone-safely in `Return Customer Lookup` — reuse the zone-aware approach already
proven in `Filter Old Sessions` (luxon `fromISO` → `fromFormat(..., { zone:
'America/Toronto' })`), or store/compare an unambiguous epoch value. Robust
version: also **scope session selection to the current `call_sid`/`conversation_id`**
and apply the timezone-safe parse to the sibling nodes for consistency. Placeholder
rejection is best achieved structurally (by correctly preferring the real session
phone) rather than by hardcoding test numbers. Final scope is a decision for the
approval step.

A detailed comparison of two implementation strategies (minimal vs architectural),
with a recommendation, is in [`INV-009-PLAN.md`](INV-009-PLAN.md).
